# 주문 저장 재설계 — 동기 DB에서 durable 로그로

## 배경

기존 주문 흐름은 주문을 DB에 동기로 저장하고, 저장하면서 받은 auto-increment id를 받아야 다음 단계로 넘어가는 구조였다. <br>
수평 확장을 붙이기 전에, 우선 무엇이 병목인지부터 측정해보기로 했다. <br>

## 1. 병목은 매칭이 아니라 동기 DB 쓰기였다

거래소라고 하면 매칭이 가장 무거울 것 같지만, 실제로 측정을 해보면 그렇지 않다. <br>
주문 흐름의 각 구간에 타이머를 붙여 시간을 재보았다. <br>

| 구간 | 평균 | 비중 |
|---|---|---|
| createOrder (DB insert) | ~2,900 ms | 76% |
| debit (HTTP → funds) | ~600 ms | ~20% |
| match (매칭 연산, Redis Lua) | ~4 ms | 0.1% |

매칭 연산은 4ms로, 전체의 0.1% 밖에 되지 않았다. <br>
시간의 대부분은 주문을 DB에 저장하는 createOrder였다. <br>
INSERT 한 줄이 왜 2.9초나 걸릴까? 200개의 동시 요청이 커넥션 풀 10개를 두고 경쟁하면서, 커넥션을 기다리는 시간이 쌓인 결과다. <br>

코드를 다시 보니 두 가지가 눈에 들어왔다. <br>
1. 매칭 Lua 스크립트는 Redis OrderBook만 읽고 쓴다. DB를 건드리지 않는다.
2. OrderBook(Redis)이 coinId, price, remainingAmount 같은 작업에 필요한 데이터를 이미 다 가지고 있다.

즉, 주문을 처리하는 데 필요한 데이터는 이미 Redis에 있었고, DB의 Order는 그 결과를 기록해두는 사본에 가까웠다. <br>
그런데 이 사본을 만드느라 hot path에서 동기로 기다리고 있었던 것이다. <br>

## 2. 1차 개선 — DB 쓰기를 hot path에서 빼기

그래서 DB 쓰기를 hot path에서 빼보기로 했다. <br>
id는 DB auto-increment 대신 Redis INCR로 채번하고, OrderBook을 Redis에 등록한 뒤, DB 반영은 인메모리 이벤트(@Async)로 뒤로 미뤘다. <br>
돈이 걸린 debit/settle 같은 동기 RPC는 즉시 정합성이 필요하기 때문에, hot path에 그대로 두었다. <br>

| | 이전 (동기 DB) | 1차 (비동기 projection) |
|---|---|---|
| 처리량 | ~50/s | 100/s |
| p95 | 4~8s | 2.8s |

처리량이 2배가 되었다. <br>
같은 DB 쓰기인데 왜 더 빨라졌을까? 200개의 요청이 커넥션 풀을 두고 경쟁하던 것을, 이제는 단일 스레드가 경쟁 없이 순차로 처리하니 오히려 효율적이었다. <br>
물론 절대 수치(100/s)는 로컬 환경의 천장 안이라 그대로 받아들이긴 어렵고([주문 흐름 병목 측정](주문%20흐름%20병목%20측정.md) 참고), 구조 변경 전후의 상대 비교(2배)가 의미가 있다. <br>

## 3. 인메모리 큐는 크래시하면 유실된다

1차 구조에는 문제가 하나 있었다. projection 큐가 인메모리라는 점이다. <br>
trading이 크래시하면, 아직 DB에 반영되지 않은 주문이 그대로 사라진다. <br>
"유실될 수 있다"는 말로만 넘어가지 않고, 실제로 얼마나 잃는지 재현해보기로 했다. <br>

projection이 밀린 상태에서 크래시하도록, trading-db를 `docker pause`로 멈춰 큐를 쌓았다. <br>
그 상태로 800건을 접수시키고, trading을 하드킬(SIGKILL)한 뒤 다시 시작했다. <br>

결과는 접수 800건, DB 반영 0건이었다. 접수된 800건이 인메모리 큐와 함께 통째로 사라진 것이다. <br>
1차 구조에는 이걸 복구할 방법이 없었다. <br>

## 4. 2차 개선 — 주문을 durable 로그에 먼저 남기기

그래서 주문이 일어났다는 사실을 디스크에 남는 로그(Kafka)에 먼저 적고, 그 다음에 나머지를 진행하도록 바꿨다. <br>

```
[hot path]
  debitKrw (RPC, 돈)
  id = Redis INCR
  OrderPlaced → Kafka append (동기, 저장 확인 대기)  ← 여기서 돌아오면 durable
  OrderBook → Redis (매칭용 작업 상태)
  match (Redis)
  체결당 settle (RPC, 돈) + TradeExecuted → Kafka append (동기)
  응답
       ↓
[컨슈머 — order-projection 그룹]
  로그 → DB 반영 (Order/Trade/fill), 반영 커밋 후 offset 커밋
```

역할이 세 층으로 나뉘었다. <br>
1. Kafka 로그 — 무슨 주문/체결이 일어났는지의 원본. 디스크에 남는다.
2. Redis OrderBook — 매칭이 도는 작업 상태. 로그에서 다시 만들 수 있는 파생물이다.
3. DB — 조회용 사본. 컨슈머가 로그를 읽어 반영한다.

여기서 두 가지가 중요하다. <br>
- **동기 append.** `send().get()`으로 브로커가 저장을 확인할 때까지 기다린다. 여기서 돌아왔다는 건 로그에 남았다는 뜻이고, 그때부터는 프로세스가 죽어도 유실되지 않는다. 만약 비동기로 보내면 "보냈는데 저장 전에 크래시" 하는 구간이 남아, 1차와 같은 문제가 생긴다.
- **dedup.** 컨슈머는 DB 반영을 커밋한 뒤에 offset을 커밋한다. 그 사이에 크래시하면, 재시작한 컨슈머가 같은 이벤트를 다시 읽는다(at-least-once). 이때 같은 이벤트가 두 번 반영되면 fillOrder가 두 번 더해져 잔고가 틀어진다. 그래서 이벤트마다 eventId를 두고, projection과 같은 트랜잭션에서 `processed_event`에 마커를 남겨 중복 반영을 막았다.

5단계에서 알림용으로는 과하다며 되돌렸던 Kafka와 dedup이, 주문 이벤트 소싱에서는 필요해 다시 들어왔다. <br>
되돌린 판단이 틀렸던 게 아니라, 알림에는 과했고 주문 로그에는 맞았던 것이다. <br>

## 5. 유실 검증과 처리량

3번과 똑같은 조건(DB pause → 800건 접수 → 하드킬 → 재시작)으로 2차 구조를 다시 측정했다. <br>

| | 접수(200) | DB 반영 | 유실 |
|---|---|---|---|
| 1차 (인메모리) | 800 | 0 | **800** |
| 2차 (durable 로그) | 800 | 800 | **0** |

같은 크래시인데, 이번엔 유실이 0이다. <br>
2차는 접수 시점에 Kafka에 저장(durable append)됐기 때문에, 재시작한 컨슈머가 로그의 offset부터 다시 읽어 800건을 전부 반영했다. <br>

처리량도 확인해봤다. <br>

| | 1차 (인메모리) | 2차 (durable 로그) |
|---|---|---|
| 처리량 | 100/s | 110/s |
| 크래시 유실 | 800/800 | 0/800 |

durable로 바꾸면 처리량이 떨어지지 않을까 걱정했는데, 실제로는 1차와 같은 ~110/s였다. <br>
동기 Kafka append가 hot path에서 5ms 정도로 저렴했기 때문에, 내구성을 얻는 대가로 치를 처리량 비용은 측정되지 않았다. <br>

## 정리

동기 DB 쓰기(병목) → Redis 우선 + 비동기(2배, 유실 위험) → durable 로그(유실 0, 처리량 손실 없음) 순서로 왔다. <br>
각 단계를 측정으로 확인하며 진행했다. 병목은 76%, 1차 개선은 2배, 유실은 800건, 2차 복구는 0건, durable의 처리량 비용은 0이었다. <br>
