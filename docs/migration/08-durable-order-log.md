7단계에서 주문 저장을 hot path에서 빼내 처리량을 2배로 만들었다. <br>
그런데 이 구조에는 문제가 하나 있었다. projection 큐가 인메모리라서, trading이 크래시하면 아직 DB에 반영되지 않은 주문이 사라진다. Redis에는 있는데 DB에는 없는 상태가 되는 것이다. <br>
이 챕터는 그 문제를 해결한다. <br>

# 인메모리 큐는 크래시하면 얼마나 유실되는가
7단계에서 주문 처리의 원본은 Redis OrderBook이었고, DB로 가는 projection은 인메모리 큐(@Async)를 탔다. <br>
둘 다 프로세스가 죽으면 사라진다. 주문이 접수됐다는 사실을 디스크에 남겨둔 곳이 없었던 것이다. <br>
사용자에게는 성공 응답을 돌려줬는데, 그 주문이 유실될 수 있는 상태였다. <br>

"유실될 수 있다"는 말로만 넘어가지 않고, 실제로 얼마나 잃는지부터 재보기로 했다. <br>
projection이 밀린 상태에서 크래시하도록, trading-db를 `docker pause`로 멈춰 큐를 쌓았다. <br>
그 상태로 800건을 접수시키고, trading을 하드킬(SIGKILL)한 뒤 재시작했다. <br>

결과는 접수 800건, DB 반영 0건이었다. 접수된 800건이 인메모리 큐와 함께 통째로 사라졌다. <br>
7단계 구조에는 이걸 복구할 방법이 없었다. 이 800건이 다음 개선의 근거가 되었다. <br>

# 주문을 durable 로그에 먼저 남기기
그래서 주문이 일어났다는 사실을 디스크에 남는 로그(Kafka)에 먼저 적고, 그 다음에 나머지를 진행하도록 바꿨다. <br>

```
[hot path]
  debitKrw (RPC, 돈)
  id = Redis INCR
  OrderPlaced → Kafka append (동기, .get으로 저장 확인 대기)  ← 여기서 돌아오면 durable
  OrderBook → Redis (매칭용 작업 상태)
  match (Redis)
  체결당 settle (RPC, 돈) + TradeExecuted → Kafka append (동기)
  응답
       ↓
[컨슈머 — order-projection 그룹]
  OrderPlaced → Order INSERT
  TradeExecuted → Trade INSERT + fillOrder + 알림
  DB 반영 커밋 후 offset 커밋(manual ack)
```

역할이 세 층으로 나뉘었다. <br>
1. Kafka 로그 — 무슨 주문/체결이 일어났는지의 원본. 디스크에 남는다.
2. Redis OrderBook — 매칭이 도는 작업 상태. 로그에서 다시 만들 수 있는 파생물이다.
3. DB — 조회용 사본. 컨슈머가 로그를 읽어 반영한다.

## 동기 append
`kafkaTemplate.send(record).get()`으로 브로커가 저장을 확인할 때까지 기다린다. <br>
이 append에서 돌아왔다는 건 주문이 로그에 남았다는 뜻이고, 그때부터는 프로세스가 죽어도 유실되지 않는다. <br>
만약 비동기(fire-and-forget)로 보내면 "보냈는데 저장 전에 크래시" 하는 구간이 남아, 7단계와 같은 문제가 생긴다. 그래서 동기로 두었다. <br>

## dedup
컨슈머는 DB 반영을 커밋한 뒤에 offset을 커밋한다. <br>
반영 후 커밋 전에 크래시하면, 재시작한 컨슈머가 그 이벤트를 다시 읽는다(at-least-once). <br>
이때 같은 이벤트가 두 번 반영되면 fillOrder가 두 번 더해져 잔고가 틀어진다. <br>
그래서 이벤트마다 eventId를 두고, projection과 같은 트랜잭션에서 `processed_event`에 마커를 남겨 중복 반영을 막았다. <br>

5단계에서 알림용으로는 과하다며 되돌렸던 Kafka와 dedup이, 주문 이벤트 소싱에서는 필요해 다시 들어왔다. <br>
되돌린 판단이 틀렸던 게 아니라, 알림에는 과했고 주문 로그에는 맞았던 것이다. <br>

# 유실 검증
문제를 확인했던 것과 똑같은 조건(trading-db `docker pause` → 800건 접수 → 하드킬 → 재시작)으로 durable 구조를 측정했다. <br>

| | 접수(200) | DB 반영 | 유실 |
|---|---|---|---|
| 7단계 (인메모리) | 800 | 0 | **800** |
| 8단계 (durable 로그) | 800 | 800 | **0** |

같은 크래시인데, 이번엔 유실이 0이다. <br>
8단계는 접수 시점에 Kafka에 저장(durable append)됐기 때문에, 재시작한 컨슈머가 로그의 offset부터 다시 읽어 800건을 전부 반영했다. <br>

부하를 주는 중에 하드킬로도 확인해봤다. 6655건이 로그에 쌓인 상태에서 죽였는데, 재시작 후 컨슈머 lag이 0으로 떨어지며 전부 반영됐고 중복 order도 0이었다(dedup). <br>
다만 Kafka 리밸런스에 약 32초가 걸렸다. 복구가 즉시는 아니지만 완전했다. <br>

# 측정 — 처리량
| | 7단계 (인메모리) | 8단계 (durable) |
|---|---|---|
| 처리량 | 100/s | 110/s |
| p95 | 2.8s | 2.5s |
| 크래시 유실 | 있음 | 0 |

durable로 바꿔도 처리량은 인메모리와 같은 ~110/s였다. <br>
동기 Kafka append가 hot path에서 5ms 정도로 저렴했기 때문에, 내구성을 얻는 대가로 치를 처리량 비용은 측정되지 않았다. <br>
절대 수치는 로컬 환경의 천장 안이라 그대로 받아들이긴 어렵고, 7단계와 8단계가 같다는 상대 비교가 요점이다. durable로 바꾸면서 처리량 손실은 없었다. <br>

# 정리
> 7단계는 처리량을 위해 projection을 인메모리로 두었고, 그 대가로 크래시하면 주문이 유실됐다(800건). <br>
> 8단계는 주문을 Kafka 로그에 먼저 남겨, 같은 크래시(SIGKILL)에서도 유실 0, 중복 0으로 복구했다. 처리량도 7단계와 같아 내구성의 처리량 비용은 없었다. <br>
> 5단계에서 알림용으로 되돌렸던 Kafka와 dedup이 여기서는 필요했다. 알림에는 과했고 주문 로그에는 맞았던 것이다. <br>
