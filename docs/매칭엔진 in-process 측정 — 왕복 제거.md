# 매칭엔진 in-process 측정 — 왕복 제거

## 배경

[매칭엔진 격리 재측정 — DB vs Redis](매칭엔진%20격리%20재측정%20—%20DB%20vs%20Redis.md)에서 per-order로 재니 Redis가 MySQL보다 ~11배 빨랐지만, Redis의 주문당 ~0.66ms는 대부분 네트워크 왕복(RTT)이었다. 매칭 자체는 µs인데 왕복이 그걸 덮었고, Redis도 외부 저장소라 그 왕복에 처리량이 묶여 있었다. 그 문서는 왕복을 없애려면 오더북을 저장소가 아니라 앱 프로세스 메모리에 직접 두면 된다고 끝냈다. 그걸 측정한다.

## 측정

오더북을 JVM 힙 자료구조(가격별 매수/매도 큐)에 두고 단일 스레드로 매칭했다. 주문이 도착하면 자기 가격 레벨에 넣고 그 자리에서 교차 쌍을 소진한다. place와 match가 힙 연산 하나로 끝나고, 네트워크 왕복이 없다.

공정성은 이전 챕터와 같은 원칙으로 맞췄다. Redis Lua와 **같은 매칭 의미**(같은 가격끼리 한 행씩 체결)를 힙에서 그대로 재현했다. 유일하게 다른 변수는 **왕복 유무** 하나다. 측정 조건도 Redis 벤치와 동일 — 주문을 하나씩 스트림으로 흘리고(prices=50, amount=1), orders/sec를 쟀다. JVM이라 JIT 워밍업 뒤에 쟀다.

## 결과

| | orders/sec | 주문당 | 조건 |
|---|---|---|---|
| Redis (외부, 왕복 2회) | ~1,520 | ~660µs | 이전 챕터 |
| **in-heap (왕복 0)** | **~30,000,000** | **~0.03µs** | 이번 |

in-heap이 약 2만 배 빠르다. 매칭 연산 자체는 주문당 30나노초다. 10,000 → 1,000,000건 내내 주문당 시간이 ~0.03µs로 일정했다(O(1) 상수, 누적 열화 없음).

## 해석

왕복이 Redis 주문당 시간의 **사실상 전부(≈99.99%)**였다. 매칭 로직 자체는 30ns라 공짜에 가깝다. 오더북을 힙에 두면 매칭도 저장소도 병목에서 아예 사라진다.

## 이 숫자의 한계

- **천장이지 실제 시스템 처리량이 아니다.** 이건 Redis 벤치와 똑같이 place+match만 격리한 값이다. 실제 주문 플로우엔 여전히 `debitKrw`/`settle` 동기 RPC와 Kafka append가 남아 있고, [주문 흐름 병목 측정](주문%20흐름%20병목%20측정.md)에서 그 주변 경로가 지배적이었다. 이 측정이 증명하는 건 매칭과 저장소가 이제 병목이 아니라는 것이다. 처리량 천장은 돈 경로(RPC)와 내구성(로그)으로 넘어간다.
- **절대 수치는 자릿수로만 읽어야 한다.** 1만 건은 0.3ms라 너무 짧아 값이 흔들린다(28~37M/s). 100만 건(33ms)이 그나마 믿을 만하고 ~30M/s다. 정밀한 값이 목적이 아니라, Redis와 자릿수 자체가 다르다는 게 요점이다.

## 결론

> 오더북을 외부 저장소에서 앱 프로세스 힙으로 옮기니 주문당 시간이 ~660µs → ~0.03µs가 됐다. 왕복이 그 시간의 거의 전부였다. 매칭 연산 자체는 30ns라, in-process로 두면 매칭도 저장소도 병목에서 빠진다. <br>
> 남는 병목은 매칭이 아니라 그 주변이다 — 돈이 걸린 동기 RPC(debit/settle)와 내구성 로그 append. 최적화 초점이 매칭 엔진에서 그쪽으로 옮겨간다.
