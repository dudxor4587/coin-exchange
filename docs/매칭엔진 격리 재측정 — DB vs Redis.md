# 매칭엔진 격리 재측정 — DB vs Redis

## 배경

[매칭엔진 성능 비교](매칭엔진%20성능%20비교.md)에서 DB와 Redis 매칭엔진을 시스템 레벨로 비교했지만, 결론은 "매칭 단독 성능은 알 수 없다"였다. 시스템 전체 병목이 wallet/trade가 공유하는 HikariCP 풀이라, 매칭엔진의 차이가 거기에 가려졌기 때문이다. 그래서 "매칭을 격리해서 재는 것"을 숙제로 남겨뒀다.

그 뒤 MSA 마이그레이션을 거치며 그 병목(공유 풀)을 없앴다 — 서비스를 분리하고, 주문 저장을 durable 로그 + projection으로 빼내고, trading을 무상태로 만들었다. 매칭을 가리던 마스크가 사라진 것이다. 이제 매칭만 격리해서 DB vs Redis를 잴 수 있다. 앱(HTTP·wallet·funds·Kafka)을 다 우회하고, 저장소(Redis / MySQL, 각 0.3 CPU)에 직접 붙어 매칭 로직만 돌렸다.

측정 설계를 두 번 고쳤다. 그 과정이 이 문서의 절반이다.

## 정정 1 — 공정성: 같은 복잡도로 맞춰야 한다

처음엔 호가창에 매칭 가능한 주문을 잔뜩 채우고 한 번에 소진시키는 방식으로 쟀다. Redis는 Lua 스크립트, MySQL은 원래 방식(호가창 로드 후 이중 루프)으로. 결과는 Redis가 200배 넘게 빨랐다. 그런데 이건 함정이었다.

N(매칭 쌍 수)을 2배로 늘리니 DB 시간이 4배로 늘었다 — **O(N²)**였다. 매칭마다 호가창을 다시 스캔하기 때문이다. Redis는 SPOP으로 한 쌍씩 꺼내니 O(N)이다. 즉 이건 "DB vs Redis"가 아니라 "**O(N²) 나이브 구현 vs O(N) 구현**"의 비교였다. 저장소 차이가 아니라 구현 격차를 재고 있었던 것이다.

그래서 DB를 Redis와 같은 O(N)으로 다시 짰다(가격별 인덱스 pop, SPOP에 대응). 그러자 격차가 200배 → 약 20배로 줄었다.

| 구현 | 복잡도 | Redis 대비 |
|---|---|---|
| 나이브 DB (호가창 재스캔) | O(N²) | ~200배 (불공정) |
| 공정 DB (인덱스 pop) | O(N) | ~20배 |

동일 구현으로 맞추자 격차가 10배 이상 줄었다. **첫 숫자(200배)를 그대로 믿었으면 틀린 결론이었다.**

## 정정 2 — 현실성: 매칭은 "한 번에"가 아니라 "주문마다"다

20배도 아직 문제가 있었다. 저 측정은 매칭 가능한 주문 수만 개를 미리 쌓아놓고 한 번에 소진하는데, **실제 거래소는 그렇게 매칭하지 않는다.** 주문이 하나씩 도착하고, 각 주문이 그때그때 호가창과 매칭될 뿐이다. 대부분의 주문은 매칭 0~몇 개다.

게다가 저 batch 측정은 Redis를 서버사이드(Lua 한 번, 클라이언트 왕복 0)로 쟀다. 실제로는 앱이 주문마다 저장소로 **네트워크 왕복**을 한다. 그리고 그 왕복은 Redis도 MySQL도 똑같이 낸다.

그래서 현실적인 모델로 다시 쟀다 — 주문을 하나씩 스트림으로 흘리고, 각 주문마다 저장소에 place + match(둘 다 왕복 포함)를 시키고, orders/sec를 쟀다.

## 현실적 결과 (per-order)

| | orders/sec | 주문당 |
|---|---|---|
| **Redis** | ~1,520 | ~0.66ms |
| **MySQL** | ~140 | ~7ms |

**Redis가 약 11배 빠르다.** batch의 20배보다 줄었는데, 이유가 중요하다.

## 해석 — 왜 20배가 11배로 줄었나

**둘 다 네트워크 왕복을 내기 때문이다.**

- **Redis ~0.66ms/주문** — 이 중 대부분이 네트워크 왕복(RTT)이다. 매칭 자체는 µs인데, 왕복이 그걸 덮는다. 즉 Redis는 여기서 **네트워크-바운드**다. 인메모리가 아무리 빨라도 왕복에 발목이 잡힌다.
- **MySQL ~7ms/주문** — 왕복 + 관계형 엔진의 처리 비용.

batch에선 Redis만 왕복이 없어 20배로 벌어졌지만, per-order로 둘 다 왕복을 내니 그 왕복이 Redis의 인메모리 우위를 부분적으로 가려 11배가 됐다.

### 느림의 정체 — fsync인가? (아니었다)

처음엔 "MySQL이 느린 건 주문마다 커밋 fsync(디스크 동기화) 때문"이라고 봤다. 그래서 `innodb_flush_log_at_trx_commit`를 풀어 재봤다.

| 설정 | 의미 | MySQL orders/sec |
|---|---|---|
| 1 (기본) | 커밋마다 fsync | ~140 |
| 2 | 1초마다 fsync (Redis AOF everysec 동급) | ~164 |
| 0 | 가장 느슨 | ~175 |

**fsync를 완전히 꺼도 140 → 175(약 25%)뿐이다.** 즉 fsync는 느림의 원인이 아니었다 — 내구성을 포기해도 Redis가 여전히 ~10배 빠르다. (fsync 가설을 세웠다가 측정으로 기각한, 세 번째 정정이다.)

진짜 정체는 **관계형 엔진의 연산당 처리 비용**이다. MySQL은 pop 하나·삭제 하나마다 SQL을 파싱·최적화·실행하고 버퍼풀·MVCC·락을 거친다. Redis는 오더북을 애초에 필요한 자료구조(셋·해시) 그대로 두고 SPOP·HSET 같은 O(1) 메모리 연산을 한다. 같은 매칭을 하는데 한쪽은 관계형 기계를 매 연산마다 돌리고, 한쪽은 자료구조를 직접 만진다. 이 차이는 튜닝으로 못 좁힌다.

여기에 하나 더 — **오더북은 "작업 상태"지 "내구성 기록"이 아니다.** 주문의 내구성은 이미 Kafka durable 로그가 맡는다(8단계). 셋·해시로 충분한 작업 상태를, 트랜잭션·내구성으로 감싸는 RDBMS에 둘 이유가 없다. 그게 저장소 선택의 불일치였다.

## 결론

> 원문이 못 냈던 답 — "매칭에서 Redis가 DB보다 빠른가"에, 격리 + 현실적 per-order 측정으로 답했다. 같은 자원에서, durability까지 풀어준 조건에서도 Redis가 약 10~11배 빠르다. 이게 매칭엔진을 DB에서 Redis로 옮긴 근거다. <br>
> 다만 그 답에 도달하며 세 번 고쳐야 했다 — DB를 O(N)으로 맞추고(공정성, 200→20배), batch 대신 per-order로 재고(현실성, 20→11배), "fsync 탓" 가설을 세웠다가 측정으로 기각했다(내구성은 원인 아님). 재는 방식과 가설을 데이터로 계속 교정한 셈이다. <br>
> 느림의 정체는 디스크도 fsync도 아니라, 관계형 엔진이 매 연산을 SQL·트랜잭션·MVCC로 처리하는 비용이었다. 오더북은 셋·해시로 충분한 작업 상태라, 그 관계형 기계 자체가 과했다.

## 남은 한계와 다음

- **절대 수치**는 로컬 환경 + host→container + 클라이언트 오버헤드로 부풀려 느리다. 상대 비교(~11배)가 요점이다.
- Redis의 주문당 시간이 **대부분 네트워크 왕복**이라는 게 핵심이다. 그걸 줄이려면 Redis를 거치는 게 아닌 직접 메모리를 사용하면 되지 않을까?
